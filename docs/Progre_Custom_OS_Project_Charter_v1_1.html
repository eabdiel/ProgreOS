Progre Custom OS Project Charter

Version 1.1 — September 2026

1. Purpose

Progre is a ProgreTech physical AI companion built on the AIPI Lite hardware platform. The project replaces the stock experience with a purpose-built Progre OS firmware that turns the device into a lightweight physical endpoint for voice interaction, expressive display behavior, Japanese-language assistance, and connection to ProgreTech services.

2. Architectural Principle

Progre is intentionally a thin endpoint. The ESP32-S3 is responsible for device hardware, interaction state, audio transport, display behavior, Wi-Fi connectivity, recovery, and the Progre protocol.

Higher-level intelligence remains outside the device: 

AIPI Lite / Progre OS
        |
        | Progre Protocol over LAN
        v
Local Progre Voice Bridge
        |
        +-- STT / TTS
        +-- Session and personality
        +-- Japanese learning
        +-- Long-term memory
        +-- Local models
        +-- Autonomous OS
        +-- ProgreTech Mesh

Progre must consume the wider ProgreTech architecture through adapters and bridges. The Progre project must not require redesigning Rend, Autonomous OS, or the ProgreTech Mesh.

4. Recovery and Safety Baseline

The original 16 MB factory firmware was captured twice and verified byte-for-byte before the first firmware write.

Factory backup SHA-256: cffb5c062b12b8e30490473b07bcdc97fc4ee46f6408eb2d28888c4747f17c02

Project rules:

  • Never burn or modify eFuses as part of ordinary development.
  • Prefer app-only firmware writes at 0x10000.
  • Preserve the original recovery image independently of development builds.
  • Use hash-verified release artifacts for controlled device updates.

6. Audio Architecture

Physical testing established that the ESP32-S3 I2S interface must operate as a paired full-duplex transport with both TX and RX continuously running.

Speaker audibility is controlled independently:

  • ES8311 DAC mute state
  • GPIO9 speaker amplifier enable

The I2S TX half must not be stopped merely to silence the speaker because doing so can interrupt the shared clock domain and prevent microphone capture.

8. Current Release and Accepted Operational State

The latest sealed release remains the Connected generation of Progre OS. The current accepted development state extends that release into a complete local conversational pipeline and is the candidate foundation for the next sealed Progre OS release.

On September 17, 2026, the physical Progre device successfully completed its first full spoken AI conversation. The onboard microphone captured the user's speech, Progre OS transported the audio over Wi-Fi to the Progre Voice Bridge, Whisper performed local speech recognition, Qwen generated the response, Piper synthesized the reply, and the resulting PCM audio was streamed back to the AIPI Lite hardware for playback through the ES8311 audio subsystem.

The acceptance test returned 94,906 bytes of streamed response audio, exceeding the earlier fixed one-second response-buffer limitation. Playback completed normally while preserving the continuously running duplex I2S architecture, after which Progre returned to normal idle and blink behavior without a panic, watchdog reset, or reboot.

The accepted conversational architecture is: person → Progre microphone → Wi-Fi → Progre Voice Bridge → Whisper → Qwen → Piper → streamed PCM → Progre speaker.

The firmware currently running on the device still identifies itself using the v0.5-connected development lineage. The conversational milestone must therefore be versioned and sealed separately rather than retroactively represented as an already published release.

9. Immediate Target — Voice Character and Conversation Polish

With bidirectional spoken conversation physically proven, the immediate target is no longer basic connectivity. The next development work focuses on making conversation with Progre feel natural, expressive, and appropriate for a small physical desktop companion.

The next bounded improvements are:

  • Give Progre a slightly higher, small-robot voice character while keeping speech clear and natural. Voice processing should remain Bridge-side and configurable rather than requiring a firmware flash.
  • Represent conversation state visually through distinct listening, thinking, speaking, and idle face behaviors.
  • Replace the temporary two-second commissioning capture limit with Talk-button duration capture suitable for normal spoken questions.
  • Move configurable voice, model, provider, listener, and connection parameters toward the future Progre Cockpit rather than hard-coding workstation settings.
  • Seal the accepted conversational implementation as a properly versioned Progre OS release after final interaction-polish acceptance.

10. Future Operator Experience and Product Direction

The command line remains the developer, diagnostic, and recovery interface beneath Progre. Once the core firmware and Bridge are stable, a Progre Cockpit will provide the normal human-facing control and provisioning experience.

The Cockpit is planned as a Flask application launched through main.py. It must sit above the proven low-level tooling rather than replace it, allowing the same underlying operations to remain inspectable and recoverable by developers.

10.1 User Configuration

  • Device status, diagnostics, restart, logs, audio tests, and display controls.
  • Speaker volume and other supported device controls.
  • Wi-Fi and network configuration.
  • Listener computer or workstation hostname/address, port, protocol, and connection parameters.
  • Local runtime and model selection, including compatible Rend, OpenClaw, Hermes, and Ollama services.
  • External API provider, endpoint, model, and required connection parameters.
  • Personality, Japanese-learning, and other user-facing Progre configuration.

Configuration should be represented as persistent data wherever practical rather than compiled firmware constants. Changing a model, listener, network, or other normal user preference should not require rebuilding Progre OS.

10.2 Device Lifecycle Management

The Cockpit is also intended to become the supported device-management interface for connected AIPI Lite and Progre hardware.

  • Detect and identify a connected compatible device.
  • Read and download a full flash backup of the firmware currently installed on the device.
  • Calculate and retain cryptographic hashes and recovery metadata for backups.
  • Upgrade an existing Progre safely using validated release artifacts.
  • Restore an appropriate recovery image when required.

10.3 AIPI Lite to Progre Provisioning

The Cockpit should support a guided provisioning workflow capable of converting compatible stock AIPI Lite hardware into a Progre device. A verified full-device backup must be created before destructive conversion or full-flash replacement. Provisioning should then install the appropriate Progre firmware components, configure the device, verify the resulting installation, and record the outcome.

This workflow is intended both for individual owners and as a future ProgreTech builder/provisioning station for preparing premade Progre devices consistently. Device records may include hardware identity, original backup hash, installed Progre version, firmware hash, provisioning date, validation results, and upgrade history.

10.4 Product Direction

Progre is being developed first as a working ProgreTech companion and engineering platform, with a possible path toward a sellable premade product. Progre OS may be released as open-source software without requiring the complete product experience to be limited to source distribution. Hardware preparation, validated provisioning, recovery tooling, Cockpit workflows, configuration, integration, testing, and the ready-to-use device experience may form part of the broader Progre product.

Commercialization must not weaken the project's recovery-first engineering model: original firmware preservation, reversible development where practical, explicit validation, and safe handling of destructive operations remain core requirements.

11. Two-Face Visual Architecture

Progre maintains exactly two installed facial assets: Idle and Talk / Active. Idle represents the waiting state. Talk / Active represents the complete interaction from Talk-button press through listening, processing, speech synthesis, and spoken playback.

Listening, processing, and speaking may remain distinct internal states, but all map visually to the single Active frame.

There is no on-device face gallery. Installing a new face pair replaces the previous pair. Idle and Talk form one logical package and should be replaced together.

The canonical hardware format is 128 × 128 monochrome artwork with a black background and white line art.

The Progre Cockpit Face Converter will accept exactly two PNG/JPG images, validate or normalize them, preview the hardware result, and install the pair. Long term, replacing these assets should not require rebuilding Progre OS.

12. Project History

September 17, 2026 — Two-Face Physical Render Checkpoint

Phase 1K established the first physical implementation of Progre's two-face visual architecture. Native monochrome Idle and Talk / Active renderers were successfully built and deployed to the AIPI Lite 128 × 128 display.

Physical testing confirmed that both states render independently on the actual hardware and that the interaction lifecycle can drive the two-state model. The implementation preserves the architectural rule of exactly two visible face states: Idle and Talk / Active.

The initial native artwork is considered a functional prototype rather than final visual acceptance. Physical photographs showed that the mascot geometry requires additional refinement to more closely match the accepted Progre reference design. That refinement is the next Phase 1K activity.

Future work remains unchanged: the Cockpit will expose face controls and ultimately provide a two-image converter for one Idle and one Talk asset. Replacement will operate on the pair rather than creating an on-device face library.

September 17, 2026 — First Full Spoken AI Conversation

Progre completed the first accepted end-to-end spoken AI conversation on the physical AIPI Lite hardware running the custom Progre OS.

During the acceptance test, a spoken question was captured through the onboard microphone and transported over local Wi-Fi to the Progre Voice Bridge. Whisper transcribed the speech locally, Qwen generated a Progre-specific response, Piper synthesized the reply, and 94,906 bytes of PCM response audio were streamed back to the device and played through its ES8311-based audio subsystem.

This test also proved the transition from the earlier fixed response-buffer prototype to continuous network response playback. The spoken response exceeded the old one-second playback ceiling and completed without disabling the paired I2S channels. Progre returned to normal idle and blink behavior afterward with no panic, watchdog reset, or reboot.

First accepted spoken identity response: “I'm Progre!”

This milestone marked the transition from a recovered and reprogrammed physical AI device into a usable ProgreTech companion capable of hearing a person, reaching a local intelligence stack, generating a contextual answer, and speaking that answer back through its own hardware.

September 17, 2026 — Progre Cockpit Operational

Following acceptance of the first full spoken conversation, the first operational Progre Cockpit was brought online as a local browser-based control plane. The Cockpit established live configuration of the Voice Bridge without requiring firmware changes or reflashing the physical device.

The accepted initial controls include Ollama model selection, Piper voice selection, voice pitch and output volume, model temperature, response-token limits, Bridge status, and live Save & Apply behavior. Configuration is stored locally and consumed by the Voice Bridge for subsequent conversations; Progre does not depend on the Cockpit browser remaining open.

Physical acceptance confirmed that Cockpit voice-character changes propagated through the Bridge and affected Progre's next spoken response as designed. This established the foundation for the broader Cockpit lifecycle model, including future networking, diagnostics, firmware management, recovery, provisioning, and ProgreTech production workflows.
